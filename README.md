# notification_relay

A notification delivery relay that sends alerts through Email, SMS, and Voice to on-call groups. Group membership is managed via LDAP sync, and access is controlled through LDAP-based RBAC.

## Overview

notification_relay acts as a relay between your alerting systems and your on-call staff. You publish a notification targeting one or more LDAP groups and one or more delivery channels (SMS, Voice, Email). The service expands group membership, creates per-member delivery records, and dispatches them through the configured providers.

Key features:

- **Multi-channel delivery** — SMS, Voice (Twilio), and Email (SMTP)
- **LDAP-backed membership** — Group membership is periodically synced from LDAP; no manual roster management
- **RBAC** — Role assignment driven by LDAP group membership
- **Audit logging** — All mutating API calls are recorded
- **Event model** — Notifications are attached to events, enabling a full timeline of alerts for an incident

## Build & Run

```bash
# Build
go build -o notification_relay ./cmd/notification_relay

# Run
./notification_relay -config config.yaml
```

On startup the service will:

1. Load and validate `config.yaml`
2. Open the SQLite database (WAL mode, single writer + reader pool)
3. Run any pending Goose migrations automatically
4. Start background goroutines: LDAP group syncer, Twilio status poller, notification dispatcher
5. Start the HTTP server

Shutdown is graceful on `SIGINT` / `SIGTERM`.

### Regenerating database queries

All database queries are generated by [sqlc](https://sqlc.dev/). After modifying `sql/`, regenerate with:

```bash
sqlc generate
```

## Configuration

All configuration lives in a single YAML file passed via `-config`. Every string value supports `${ENV_VAR}` interpolation.

A minimal working configuration requires `database.path`, `ldap.primary_url`, `ldap.bind_dn`, `ldap.bind_password`, `ldap.user_base_dn`, `ldap.group_base_dn`, and at least one entry in `ldap.sync_groups`.

```yaml
database:
  path: /var/lib/notification_relay/db.sqlite

http:
  listen_addr: ":8080"

ldap:
  primary_url: "ldaps://dc01.corp.example.com"
  bind_dn: "CN=svc-relay,OU=ServiceAccounts,DC=corp,DC=example,DC=com"
  bind_password: "${LDAP_PASS}"
  user_base_dn: "OU=Users,DC=corp,DC=example,DC=com"
  group_base_dn: "OU=Groups,DC=corp,DC=example,DC=com"
  sync_groups:
    - grp-oncall
  roles:
    admin:
      - grp-admins
    publisher:
      - grp-oncall
    reader:
      - grp-monitoring

smtp:
  host: smtp.example.com
  port: 587
  username: noreply@example.com
  password: "${SMTP_PASS}"
  from_address: noreply@example.com
  tls_mode: starttls

twilio:
  account_sid: "ACxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
  auth_token: "${TWILIO_TOKEN}"
  from_number: "+15005550006"
```

### Database

| Field | Default | Description |
|---|---|---|
| `path` | *(required)* | Path to the SQLite database file |
| `max_reader_conns` | `4` | Size of the read-only connection pool |

SQLite is opened in WAL mode. A dedicated single-connection writer prevents `SQLITE_BUSY` errors under concurrent load.

### HTTP Server

| Field | Default | Description |
|---|---|---|
| `listen_addr` | `:8080` | TCP address to bind (e.g. `"0.0.0.0:9000"`) |
| `read_timeout` | `30s` | Maximum duration for reading the full request |
| `write_timeout` | `30s` | Maximum duration for writing the response |
| `shutdown_timeout` | `15s` | Grace period for in-flight requests on shutdown |

### LDAP

LDAP drives both authentication and group membership. All API requests use HTTP Basic Auth; credentials are validated against LDAP on each request (subject to caching).

| Field | Default | Description |
|---|---|---|
| `primary_url` | *(required)* | LDAP server URL — `ldap://` for plaintext, `ldaps://` for TLS |
| `backup_url` | — | Optional fallback server. Must use the same scheme as `primary_url`. Used automatically if primary is unreachable. |
| `bind_dn` | *(required)* | Distinguished name of the service account used for directory lookups |
| `bind_password` | *(required)* | Password for the service account. Use `${ENV_VAR}` to avoid storing secrets in the config file. |
| `user_base_dn` | *(required)* | Root DN under which user objects are searched (e.g. `"OU=Users,DC=corp,DC=example,DC=com"`) |
| `group_base_dn` | *(required)* | Root DN under which group objects are searched |
| `group_filter` | `(objectClass=group)` | LDAP filter applied when looking up groups |
| `sync_groups` | *(required)* | List of group CNs whose membership is mirrored into the local database |
| `roles` | — | Maps role names to lists of LDAP group CNs (see [Authentication & RBAC](#authentication--rbac)) |
| `sync_interval` | `15m` | How often to refresh group membership from LDAP |
| `dial_timeout` | `10s` | Timeout for establishing an LDAP connection |
| `tls_skip_verify` | `false` | Skip TLS certificate verification for `ldaps://` connections. Not recommended for production. |
| `auth_cache_size` | `256` | Maximum number of authenticated principals to cache. Set to `0` to disable caching. |
| `auth_cache_ttl` | `30s` | How long a cached authentication result is considered valid |
| `page_size` | `500` | LDAP result page size for paginated queries |

### SMTP

| Field | Default | Description |
|---|---|---|
| `host` | — | SMTP server hostname |
| `port` | — | SMTP server port (typically `25`, `465`, or `587`) |
| `username` | — | Authentication username |
| `password` | — | Authentication password. Supports `${ENV_VAR}` interpolation. |
| `from_address` | — | Envelope and header `From` address |
| `tls_mode` | `starttls` | Encryption mode: `none`, `starttls`, or `tls` |

### Twilio

Twilio configuration is optional. If omitted, SMS and Voice delivery will not be available.

Because outbound webhooks may be blocked by firewalls, delivery status is tracked by polling the Twilio API rather than relying on webhook callbacks.

| Field | Default | Description |
|---|---|---|
| `account_sid` | — | Twilio Account SID (`ACxxxxxxx...`) |
| `auth_token` | — | Twilio Auth Token or API key secret. Supports `${ENV_VAR}` interpolation. |
| `token_sid` | — | Twilio API Key SID (optional, used with API key auth instead of Auth Token) |
| `from_number` | — | Twilio phone number to send from (E.164 format, e.g. `+15005550006`) |
| `poll_interval` | `30s` | How often to query Twilio for updated delivery status |
| `poll_attempt_limit` | `10` | Maximum number of failed poll attempts before a delivery is marked `poll_failed`. Set to `0` for unlimited retries. |

### Notifications

Controls the dispatcher worker pool and retry behavior.

| Field | Default | Description |
|---|---|---|
| `worker_count` | `4` | Number of concurrent dispatcher goroutines |
| `retry_limit` | `3` | Maximum delivery attempts per record before marking as failed |
| `retry_delay` | `60s` | Base delay between retries. Actual delay uses exponential backoff: `retry_delay × 2^(attempt-1)` |
| `delivery_timeout` | `30s` | Per-delivery operation timeout |

### Logging

| Field | Default | Description |
|---|---|---|
| `level` | `info` | Log verbosity: `debug`, `info`, `warn`, or `error` |
| `format` | `json` | Output format: `json` or `text` |

## Authentication & RBAC

All API endpoints require HTTP Basic Auth. Credentials are validated against LDAP using the configured service account to locate the user's record and then rebinding as that user to verify the password.

Roles are derived from LDAP group membership at authentication time and mapped via `ldap.roles` in the config:

```yaml
ldap:
  roles:
    admin:
      - grp-admins
    publisher:
      - grp-oncall
    reader:
      - grp-monitoring
```

| Role | Permissions |
|---|---|
| `admin` | Full access: read, publish, and administrative operations (templates, audit log) |
| `publisher` | Publish notifications and events; read all resources |
| `reader` | Read-only access to events, notifications, deliveries, and groups |

A user's effective role is the highest-privilege role for which they are a member of at least one of the mapped LDAP groups.

### Auth Caching

To reduce LDAP load, successful authentications are cached in an in-process LRU. Configure the cache size and TTL via `ldap.auth_cache_size` and `ldap.auth_cache_ttl`. Set `auth_cache_size: 0` to disable caching entirely.

## LDAP Group Sync

Group membership is periodically mirrored from LDAP into the local `group_members` table. This is what allows the notification dispatcher to resolve group names to individual members with their contact details.

**What is synced per member:**

- `sAMAccountName` (username)
- `displayName`
- `mail` (email address)
- `mobile` (mobile phone, used for SMS and Voice)
- Work phone (used as a fallback for Voice)

**Sync behavior:**

- Runs at startup and then every `ldap.sync_interval` (default `15m`)
- Each sync is a full delete-and-reinsert for the group, wrapped in a transaction — the table always reflects a complete snapshot from LDAP
- If the primary LDAP server is unreachable, the sync automatically retries against `backup_url` (if configured)
- Pagination is used for large groups (`ldap.page_size`, default `500`)

Only groups listed in `ldap.sync_groups` are synced. The `ldap.roles` mapping is evaluated at authentication time against the user's live `memberOf` attribute and is independent of the sync.

## Notification Flow

1. A publisher calls `POST /api/v1/notifications` targeting one or more groups and channels.
2. The service creates a notification record and returns `202 Accepted` with a `notification_id`.
3. A dispatcher worker picks up the job, expands each group to its current members from the `group_members` table, and creates one delivery record per member per channel.
4. Each delivery is dispatched to the appropriate provider:
   - **SMS** — Twilio Messaging API using the member's `mobile_phone`
   - **Voice** — Twilio Voice API using `mobile_phone`, falling back to `work_phone`
   - **Email** — SMTP using the member's `email_address`, rendering the specified template
5. Failed deliveries are retried up to `notify.retry_limit` times with exponential backoff.
6. Twilio delivery statuses are updated asynchronously by the background poller (`notify.poll_interval`).

Members missing the required contact field for a channel (e.g. no email address) are skipped for that channel.

## Email Templates

Email templates use Go's `text/template` syntax. Templates are managed via the API and stored in the database.

**Create a template:**

```http
POST /api/v1/templates
Content-Type: application/json
Authorization: Basic <admin-credentials>

{
  "template_name": "incident-alert",
  "subject": "Incident: {{.incident_name}}",
  "body": "<h1>{{.incident_name}}</h1><p>{{.description}}</p>",
  "required_vars": ["incident_name", "description"],
  "description": "Standard incident notification template"
}
```

**Use a template in a notification:**

```json
{
  "groups": ["grp-oncall"],
  "channels": ["email"],
  "email_template": "incident-alert",
  "email_vars": {
    "incident_name": "Database Unreachable",
    "description": "Primary database is not responding."
  }
}
```

If a notification specifies `email` as a channel, `email_template` is required. All `required_vars` defined on the template must be present in `email_vars`.

## API Reference

All endpoints are under `/api/v1/`. Authentication is HTTP Basic Auth on every request.

### Notifications

| Method | Path | Role | Description |
|---|---|---|---|
| `POST` | `/api/v1/notifications` | publisher | Publish a notification to groups |
| `GET` | `/api/v1/notifications/{notification_id}` | reader | Get notification details |
| `GET` | `/api/v1/notifications/{notification_id}/deliveries` | reader | List delivery records for a notification |

**Publish a notification (`POST /api/v1/notifications`):**

```json
{
  "event_id": "INC-2026-042",
  "event_url": "https://incidents.example.com/INC-2026-042",
  "event_name": "Database Unreachable",
  "event_description": "Primary DB is not responding to health checks.",
  "event_severity": "critical",
  "start_time": "2026-04-15T10:00:00Z",
  "groups": ["grp-oncall"],
  "channels": ["sms", "email"],
  "message": "CRITICAL: Database unreachable. Check runbook immediately.",
  "email_template": "incident-alert",
  "email_vars": {
    "incident_name": "Database Unreachable"
  }
}
```

Returns `202 Accepted` with `notification_id`, `event_id`, `groups`, and `channels`.
